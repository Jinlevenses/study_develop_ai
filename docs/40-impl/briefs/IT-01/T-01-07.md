### 4.3 `.fpack` 검증 (`infra/packs/fpack-reader.ts` — 부모·job 공용)

`readFpack(filePath, opts: { maxBytes: 64 MiB }): Result<VerifiedFpack, FpackFault>`, `FpackFault = { reason: <아래 코드>, detail }` — 하나라도 어기면 err(쓰기 0).

1. 일반 파일·확장자 `.fpack`·크기 ≤ 64 MiB(`file_invalid`·`too_large`). `source_sha256 = sha256(파일 바이트)`.
2. **ustar**(`ustar.ts`, T-01-03 §4.8 ⑦ 역방향): 512바이트 헤더마다 checksum(chksum 칸을 공백 8개로 놓고 바이트 합) 일치 · typeflag `'0'` · magic `ustar\0` · size 8진 · 항목이 **정확히** `manifest.json`→`bundle.jsonl`→`report.json`→`layout.json` 순 · 데이터 512 정렬 · 끝 0블록 2개, 그 뒤 바이트 0 또는 0 패딩만(`tar_invalid`).
3. manifest = `FpackManifest.parse(JSON.parse(utf8))`(`manifest_invalid`) · `manifest_hash = sha256(manifest.json 항목 바이트)` · `files[]` 3개의 `sha256`·`bytes` = 실제 항목(`file_hash_mismatch`).
4. `bundle.jsonl`: `\n`으로 끝나야 하고 줄 ≤ 1 MiB · 줄마다 `BundleRecord.parse(JSON.parse(줄))`(`record_invalid:<line>`) · `content_hash`가 있는 kind(gate_result 제외)는 `sha256(canonicalJson(레코드 − content_hash))` 일치(`record_hash_mismatch:<line>`).
5. **merkle**(`merkle.ts`): leaf = `sha256(줄 바이트, \n 제외)` 32바이트 → leaf 바이트 오름차순 → 레벨마다 `sha256(0x01 ‖ L ‖ R)`, 홀수 마지막은 그대로 올림 → hex = `manifest.merkle_root`(`merkle_mismatch`). 검증 벡터: `['a']`→`ca978112ca1bbdcafac231b39a23dc4da786eff8147c4e72b9807785afee48bb` · `['a','b','c']`(순서 무관)→`535ad6d3811dc338ec7f974ee523fcc19a0fb7d68204c21818a93b0d572c4a21` · `['{"kind":"edge"}','{"kind":"track"}']`→`516a314758a680455f4dfaba37495f4586cd17278bdc32826f807ed012c8eab3`.
6. 일관성(`manifest_inconsistent`): track 레코드 정확히 1개이고 `track_id = manifest.track` · 모든 concept `track_id = manifest.track` · `manifest.counts.{concepts,kus,misconceptions,items}` = 해당 kind 레코드 수, `cases` = case 레코드 수.
7. report = 로컬 `PackReportSlice = z.looseObject({ kpi: PackKpi, tier_counts: S({A,B,C}), cap_blockers: z.array(FeasibilityBlocker).max(100) })`(packc 소유 문서 — 나머지 키는 보존만, `report_invalid`). layout = JSON 객체이기만 하면 됨.
- `VerifiedFpack = { manifest, manifest_hash, source_sha256, report_canonical: string, records: readonly BundleRecord[], concept_ids, ku_hashes: ReadonlyMap<ku_id, content_hash>, concept_hashes: ReadonlyMap<concept_id, content_hash> }`.

### 4.4 설치 유스케이스 (`application/catalog/install-pack.ts`, PGM-CT-001 — IF-CT-001·002)

1. **원천 해석**: `bundled` → `packsDir`의 `*.fpack`(이름 `<pack_id>@<version>.fpack`), `track`이 있으면 그 팩만, 같은 팩 여러 버전이면 semver 최댓값 1개, 0개면 `CT-NOTFOUND-003` · `file` → 절대 경로 1개 · `user_dir` → `CT-VAL-011`(detail `user_dir unsupported in R0`) [Brief 결정 — R3].
2. **진행 중·슬롯**: 이 installer에 진행 중 요청이 있거나 해당 팩에 `state IN ('loading','ready')` 행 → `CT-CONFLICT-013` · `jobs.isBusy()` → `CT-DEP-002`.
3. **검증**(전부 먼저, 하나라도 실패 = 요청 전체 `CT-VAL-011`, detail = `FpackFault.reason`, 쓰기 0): `readFpack` · `manifest.channel = req.channel` · 활성 설치에 있던 `concept_id`가 새 번들에 없음 = `concept_removed:<id>`(안정 ID, FR-CUR-004 — 폐기는 `deprecated_by`로만).
4. **판정**(`domain/catalog/install/decide.ts` `decideInstall(candidate, rowsOfPack, allowDowngrade)`): 같은 버전 active·같은 manifest_hash → `noop`(행·이벤트 0, view `activated`) · 같은 버전 active/retired·다른 hash → `CT-CONFLICT-013` · 같은 버전 retired·같은 hash → `reactivate`(job 없이 §4.6만) · 활성 버전 > 후보 ∧ `!allow_downgrade` → `CT-CONFLICT-013` · 그 밖 → `load`. semver 비교 = SemVer 2.0(사전 릴리스 < 릴리스).
5. **행 생성**(1 tx, `ingest/install-rows.ts`): 팩마다 `install_id = newId()`, `ct_pack` INSERT(`state 'loading'`, `channel = req.channel`, `track_id = manifest.track`, `schema_v`, `packc_version`, `manifest_hash`, `merkle_root`, `source_sha256`, `manifest_json = canonicalJson(manifest)`, `report_json = report_canonical`, `offline_cap_level`, `created_at`, `ext = {"catalog.request_id": req.install_id, "catalog.previous_version": <활성 버전|null>}`). → 202 view(`state: 'loading'`).
6. **백그라운드**(promise 보관 + `.catch` 로그 — floating 0): 팩 순서대로 `jobs.run('pack-load', { home, install_id, fpack_path, expected_sha256 }, { timeoutMs })` → ok면 §4.6 활성화 tx → 다음 팩. job 실패·활성화 예외 → 그 행 `state 'failed'`, `state_reason` = `pack_load:<kind|code>` · `ext."catalog.error_id" = newId()` · `ext."catalog.finished_at"`, 남은 팩은 계속 진행하지 않고 `failed('aborted')` [Brief 결정 — 요청 단위 순서 보장]. 이미 활성화된 팩은 유지.
7. **view 재구성**(`domain/catalog/install/view.ts`): 같은 `catalog.request_id` 행들 → 진행 중 phase(메모리) 우선, 아니면 `failed` 하나라도 → `failed`(problem = `{ type: 'urn:fathom:problem:ct-internal-900', title, status: 500, code: 'CT-INTERNAL-900', detail: state_reason, error_id: ext 값, request_id: req.install_id, retryable: false }`) · 전부 active/retired → `activated` · 그 밖 → `loading`. `packs[] = {pack_id, track, version, previous_version, conflicts: 0}`. `noop` 요청(행 없음)은 메모리 최근 64건 맵으로만 조회 [Brief 결정]. `started_at` = 최소 `created_at`, `finished_at` = 종료 시 최대값, 진행 중 null. 출력은 `PackInstallView.parse`.

### 4.5 job `pack-load` (`jobs/pack-load.ts` + `application/catalog/ingest/pack-load-run.ts`, PGM-CT-002)

- `makePackLoadJob(deps: { readonly ingest: IngestRegistry; readonly runtime?: () => Promise<Pick<SqliteRuntime, 'openDb'>>; readonly clock?: Clock }): JobDefinition` — args `PackLoadArgs = S({ home, install_id: Ulid, fpack_path, expected_sha256: Sha256Hex })`, DB = `homePath(home,'data','content.db')`, 옵션 = `CONTENT_DB`의 synchronous·recursiveTriggers(`infra/db/open.ts` import). 핵심 로직은 테스트용으로 `runPackLoad(db, deps, args, ctx)`로 분리.
1. 1 tx: 대상 행이 `state = 'loading'`인지 확인(아니면 `install_state_invalid`) · **같은 pack_id의 `failed` 설치 정리**: 핸들러마다 `purge(db, id)` → `DELETE FROM ct_pack WHERE install_id = :id`(설치 범위 행 CASCADE).
2. `readFpack` 재실행 + `source_sha256 = expected_sha256`(TOCTOU, 아니면 `source_changed`).
3. 레코드를 번들 순서로 **500건씩** `db.tx` 1회: catalog 8종은 `load-records.ts` INSERT(일반 INSERT — 설치 범위가 새것이므로 중복 = 번들 결함 → 실패), 핸들러 kind는 배치 안 순서대로 묶어 `handler.ingest`. 배치마다 `ctx.progress(pct, 'load')`, `ctx.signal.aborted`면 `throw new Error('cancelled')`.
   - 행 매핑(번역 규칙 ①②③): `aliases`→`aliases_json` · `tags`→`tags_json` · `diagrams`→`diagrams_json` · `sources`→`sources_json` · `source_refs`→`source_refs_json` · `related_ku_ids`→`related_ku_ids_json` · `dims`→`dims_json` · `edge_kind`→`ct_concept_edge.kind` · `source_type`→`ct_source.kind` · `ext` = `canonicalJson(record.ext)`, `ext_v = 1`, JSON 열 = `canonicalJson(값)`, boolean → 0/1.
4. **재적용 자리**(DB-01 §5.3.2-3·ADR-004 §5): `ct_pack_delta`에 그 팩 `status='applied'` 행이 있으면 실패 `delta_reapply_unsupported`(IT-04 수입 WP 전 데이터 손실 방지) · `ct_overlay_event` 행 수를 결과 `overlay_events`로 보고(조회 = 팩 ⊕ 오버레이가 읽기 시점 합성이므로 IT-01 적재에는 영향 0; 충돌 탐지 = IT-03) [Brief 결정].
5. 1 tx: `UPDATE ct_pack SET state='ready', ready_at=:now WHERE install_id=:id AND state='loading'` — `changes ≠ 1`이면 invariant.
6. 결과 `{ install_id, records: {<kind>: n}, batches, overlay_events, duration_ms }`. 검색 문서(`ct_search_doc`)·레이아웃(`ct_layout`)은 적재하지 않는다(검색 = IT-02 WP, layout `status: deferred`) [Brief 결정].

### 4.6 활성화 1 tx (`application/catalog/ingest/activate.ts`, PGM-CT-001·004 — 부모, `outbox.db.tx` 하나)

1. 새 설치 행(`ready`, reactivate면 `retired`) · `prev = ct_pack_active(pack_id)`.
2. `catalog_version = max(json_extract(ct_pack.ext,'$."catalog.version"')) + 1`(없으면 1) [Brief 결정 — DDL에 열이 없어 `ext`로, CR-41 단조 버전].
3. 개념 차분(`domain/catalog/install/diff.ts`): prev 없음 또는 prev에 없던 개념 = `published` · `content_hash` 다르고 `deprecated_by`가 새로 non-null = `deprecated` · tier가 C→B→A 방향으로 오름 = `tier_promoted` · 그 밖 hash 차이 = `revised` · 같음 = 변경 없음. 개념 `ext."catalog.version"` = 변경이면 `catalog_version`, 아니면 prev 행 값(`UPDATE ct_concept SET ext = json_set(ext, '$."catalog.version"', :v) WHERE install_id=:i AND concept_id=:c`). KU 차분 = 새 KU 또는 hash 차이 → `changed_ku_ids`.
4. prev 행 `state='retired', retired_at` · 새 행 `state='active', activated_at, ext=json_set(…'catalog.version')` · `ct_pack_active` UPSERT(`install_id`, `previous_install_id = prev`, `switched_at`) · 핸들러마다 `activate(db, …)`.
5. outbox(`appendEvent(outbox, …)`, `correlation_id = req.install_id`): 변경 개념마다(concept_id 오름차순) `catalog.concept.changed` v1 `{ change, concept: ConceptRef, pack_id, version }` → 마지막에 `catalog.pack.activated` v1 `{ pack_id, track, version, channel, manifest_hash, merkle_root, previous_version, changed_concept_ids(정렬), changed_ku_ids(정렬), offline_cap_level, catalog_version, activated_at }` [Brief 결정 — 개념 스냅샷이 활성 표지보다 먼저 도착]. 2,000·20,000 상한 초과 = invariant(IT-01 팩 규모 ≤ 300 개념).
6. **ConceptRef**(`application/catalog/concept-ref.ts`, 활성화·export 공용): `{ concept_id, track: track_id, level, tier, knowledge_type, title_ko, title_en, summary_ko, prereq_ids: (kind='prereq' ∧ to = 이 개념)의 from 정렬, required_for_level, aliases, deprecated_by, volatility, tags, version: ext."catalog.version", content_hash }` → `ConceptRef.parse`.
- 롤백: 이 tx 안 예외(핸들러 activate 포함) = 포인터·상태·outbox 전부 불변, 새 행은 §4.4-6에 따라 `failed`. `noop`은 이 단계를 타지 않는다.

### 4.8 CurriculumExport (`application/catalog/export-curriculum.ts`, PGM-CT-004 — IF-CT-007)

`exportCurriculum(db, query: CurriculumExportQuery, clock): Generator<string>` — 줄 = `canonicalJson(line) + '\n'`, 각 줄은 내보내기 전에 `CurriculumExportLine.parse`. 시작 시 활성 데이터를 `.all()`로 먼저 읽어 둔다(제너레이터 대기 중 쓰기와 섞이지 않게).
