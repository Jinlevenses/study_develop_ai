- **[Brief 결정]** ARC의 `appendEvent(tx, …)`의 `tx` = `Outbox` 핸들(DB + 시계 + 페이로드 레지스트리 + 추적 컨텍스트). 모듈 전역 상태 없이(STD-TS-16) relay 깨우기와 traceparent 자동 복사를 하기 위함. **호출자는 반드시 `outbox.db.tx(() => { …상태 변경…; appendEvent(outbox, {...}) })` 안에서 부른다**(같은 `BEGIN IMMEDIATE`, STD-EVT-10 — 런타임 검사 수단이 없으므로 JSDoc + IT로 보증).
- `append`: `payloads[type]?.[schema_version]` 없음 → `invariant: unknown event <type>@v<n>` · `correlation_id`·(있으면)`causation_id`가 `isUlid` 아님 → invariant · 스키마 `parse`(실패 = 던짐, ZodError를 `cause`로) → `canonicalJson(parsed)` → `APPEND_OUTBOX` 실행(`event_id = newId ?? ulid`, `occurred_at = clock.now()`, `traceparent = currentTraceparent()`) → `seq = lastInsertRowid`(number로 — `Number.isSafeInteger` 아니면 invariant) → `onAppended()` 호출 → 반환. `onAppended`는 relay의 `kick`(setImmediate 지연이므로 tx COMMIT 뒤에 실행된다; ROLLBACK이면 relay가 빈 배치를 볼 뿐).

#### 4.1.3 relay (`relay.ts`, ARC §8.3 relay 규칙, DB-01 §4.2) — STD-TS-27 허용 상태 객체

- 시작: `routing`의 목적지마다 `ENSURE_DELIVERY`(한 tx) → `setInterval(drainAll, pollMs).unref()`(500ms 안전망). `kick()` = 이미 예약돼 있지 않으면 `setImmediate(drainAll)` 1회(여러 append를 한 번으로 합침).
- 목적지 처리(**목적지별 in-flight 1** — `Set<dest>`로 중복 진입 차단, 같은 목적지가 처리 중이면 그 회차는 건너뜀): `outbox_delivery` 행 읽기(`[Brief 결정] DELIVERY_GET`) → `now < next_attempt_at`이면 건너뜀 → `RELAY_BATCH`(`:types_json = JSON.stringify(types)`) →
  - **배치 0행**: `[Brief 결정] RELAY_SKIP_TO_HEAD` = `UPDATE outbox_delivery SET last_acked_seq = max(last_acked_seq, (SELECT coalesce(max(seq), 0) FROM outbox)), updated_at = :now WHERE dest = :dest` — 구독하지 않는 타입만 남은 꼬리 구간을 전진시켜 정리가 막히지 않게 한다(단일 writer라 커밋 순서 = seq 순서).
  - **notify 목적지**: `occurred_at < now − 60_000`인 행은 보내지 않는다. 배치 전부가 오래됐으면 마지막 행 seq로 `RELAY_ACK` 하고 끝.
  - envelope 구성: `{event_id, type, schema_version, producer: svc, producer_seq: seq, occurred_at, correlation_id, causation_id, traceparent, payload: parseJsonStrict(payload)}` → `transport.deliver(dest, {producer: svc, events}, attempt = attempts + 1)`.
  - 결과 처리 **[Brief 결정 — 부분 ack 시 시도 횟수가 리셋되면 dead-letter가 영원히 오지 않으므로]**: ① `ok` 이고 `acked_through_seq ≥ 마지막 전송 seq` → `RELAY_ACK`(attempts 0) ② `ok` 이지만 그보다 작음(소비자가 시도 < 3 실패로 앞부분만 ack, IF §3.3-3) → `[Brief 결정] RELAY_PARTIAL` = 커서 `max(last_acked_seq, :acked)` + `attempts = CASE WHEN :acked > last_acked_seq THEN 1 ELSE attempts + 1 END` + 백오프 + `last_error_code='INBOX-PARTIAL'` ③ `INBOX-HALT`(503 `-DEP-910`) → 같은 `RELAY_PARTIAL`(코드 `INBOX-HALT`, `acked_through_seq` 있을 때) ④ 그 밖 실패 → `RELAY_FAIL`. 커서는 **`max()`로만 전진**(역행 0).
  - 백오프: `delay = min(30_000, 500 × 2^(attempts_after − 1))`(지터 없음 — 결정적), `next_attempt_at = now + delay`. 값이 DB에 있으므로 재시작 후에도 이어진다(UT-SK-013).
  - 배치가 100행이었고 성공이면 같은 목적지를 `setImmediate`로 바로 다시 처리.
- `pause()`: 이후 회차는 아무것도 하지 않음(진행 중 1건은 끝까지) · `resume()`: 해제 + `kick()` · `drainOnce()`: 모든 목적지를 1회 처리하고 끝날 때 resolve(일시정지면 즉시 resolve) · `stop()`: 타이머 해제 + 진행 중 처리 대기.
- 로그: 실패마다 `warn` `{event: 'relay.delivery.failed', dest, attempts, code}`(STD-NAM-80), 성공 로그 없음. 메트릭: `relay_delivery_failures_total{dest}` 카운터 · `outbox_pending{dest}`·`outbox_oldest_age_ms{dest}` 게이지(`collectGauges`에서 `[Brief 결정] OUTBOX_PENDING` = `SELECT count(*) AS n, min(occurred_at) AS oldest FROM outbox WHERE seq > :last_acked_seq AND type IN (SELECT value FROM json_each(:types_json))`).

- **[Brief 결정]** ARC 이름 `inboxPlugin`을 유지하되 반환은 Fastify 비의존 처리기다(라우트 등록·인증·본문 검증·quiesce 게이트는 service 모듈 §4.4가 한다).
- **실패 표지 [Brief 결정]**: inbox 내부 실패는 `new Error('<짧은 문구>', { cause: { inbox_code: <코드>, error: <원 오류|null> } })`로 던지고, 분류기 `inboxErrorCode(e: unknown): string`이 `cause.inbox_code`(문자열)를 읽는다. 코드 3종 = `VAL-SCHEMA` · `HANDLER-ASYNC` · `HANDLER-MISSING`.
- `defineInboxHandler`의 `run`: `payloads[envelope.schema_version]` 없음 → `VAL-SCHEMA` 표지로 던짐 → 스키마 `parse`(ZodError → `VAL-SCHEMA` 표지, 원 ZodError는 `cause.error`) → `handle(envelope, parsed, db)` → 반환값이 thenable이면 `HANDLER-ASYNC` 표지로 던짐(tx가 ROLLBACK). payload 검증은 **여기서 1번만**(STD-API-27).
- 생성 시 검사: `durable`인데 `deps.db === null`·구독에 `mode: 'notify'` 있음, `notify`인데 `durable` 구독 있음 → invariant(createService가 기동 시 fatal 70). 구독 타입에 핸들러가 없으면 `error` 로그 1줄(`inbox.handler.missing`, 타입 목록)만 — 그 이벤트는 처리 시 독 이벤트(`HANDLER-MISSING`)가 된다(halt면 정지, dead_letter면 격리 — **유실 0**) **[Brief 결정]**.
- `process` 사전 검사: `caller !== delivery.producer` → `reject producer_mismatch`(service가 403 `ACL-900`) · `producer_seq` 엄격 증가 아님 → `reject producer_seq_order`(400 `VAL-900`).
- **durable**: 이벤트마다(순서대로, 이벤트 사이 `await setImmediate()` 양보 — 한 틱 ≤ 50ms, STD-ASY-06) `db.tx(() => …)` 1개:
  1. `INBOX_SEEN` 있음 → 아무것도 안 함(성공으로 셈).
  2. 구독 없음 또는 `schema_version ∉ schema_versions` 또는 `on_poison === 'drop'` → `INBOX_RECORD` + `INBOX_WATERMARK`(건너뜀도 기록 — 워터마크가 복원 되감기의 원천이므로) + tx 밖에서 `warn` `inbox.event.skipped`. **[Brief 결정]**
  3. 핸들러 `run(envelope, db)` → 성공 시 같은 tx에서 `INBOX_RECORD` + `INBOX_WATERMARK`.
  4. 예외 → tx ROLLBACK(sqlite `tx`가 함) → 오류 코드 = 표지(`VAL-SCHEMA`·`HANDLER-ASYNC`·`HANDLER-MISSING`) 또는 `AppError`면 `HANDLER-<code>` 또는 `HANDLER-EXCEPTION`. `error_detail` = `redactString(message)`의 앞 500자, 줄바꿈 이후 제거(스택 0).
     - `dead_letter` + `attempt ≥ 3` → 별도 tx: `[Brief 결정] INBOX_DEAD_INSERT`(`INSERT INTO inbox_dead(event_id, producer, producer_seq, type, envelope, error_code, error_detail, attempts, failed_at) VALUES (…)`, envelope = `canonicalJson(envelope)`) + `INBOX_RECORD` + `INBOX_WATERMARK` → `inbox_dead_total` +1, `error` `inbox.event.dead_lettered` → **계속**.
     - `dead_letter` + `attempt < 3` → 중단, `ack`(직전 성공 seq).
     - `halt` → 중단, `halt`(직전 성공 seq), `inbox_halted{producer}` = 1, `error` `inbox.path.halted`. 이후 그 생산자의 이벤트가 하나라도 성공하면 0으로.
  - "직전 성공 seq"가 없으면 `max(0, 첫 이벤트 producer_seq − 1)`.
  - 배너 = 메트릭: ops-api가 15s마다 `inbox_dead_total`·`inbox_halted`를 수집해 `ops.health.changed`를 낸다(ADR-015 §3·§5) **[Brief 결정 — shared-kernel은 소비자이므로 ops 이벤트를 직접 만들 수 없다]**.
- **notify**(gateway): tx·dedupe 없이 구독 타입만 걸러 `notify(events)` 1회 호출, 예외는 `error` 로그 후 무시, 항상 `ack`(마지막 `producer_seq`) — at-most-once(IF §3.3-4).

#### 4.3.4 `--mode` 분기 (`modes.ts`)
- argv(`port.argv`) 파싱 — `--key=value`·`--flag`만, 모르는 키 = 64: `--mode=serve|migrate|restore|verify|job`(**없으면 serve** [Brief 결정 — supervisor·k8s 진입 단순화]) · migrate: `--dry-run`·`--db-copy-dir=<abs>` · restore: `--from=<abs>`·`--rewind-cursors=<json>` · verify: `--replay`·`--db-copy-dir=<abs>` · job: `--job=<JobName>`. 형식 오류 → 64(로그 `mode.args.invalid`, IPC 없으면 `fatal` 송신 생략).
- serve 외 모드는 **봉투를 기다리지 않는다**: `home = resolveFathomHome()`(supervisor가 자식 env에 `FATHOM_HOME`을 넣는다, ADR-012 §2), 로거 = `createLogger(svc, {level:'info', bootId: null, clock})`(job은 `job: <name>`). 결과는 `info` 로그 1줄(`event: 'mode.<mode>.completed'`, 요약 필드) + 종료 코드 — supervisor는 stdout 꼬리로 `svc.run_mode.result`를 만든다.
- **migrate**(`mode-migrate.ts`, DB-01 §11.2): DB마다 `dir = --db-copy-dir ?? homePath(home,'data')`, `dirs = [{module:'_infra', dir: infraMigrationsDir()}, ...db.migrations]`(`infraMigrationsDir()` = `fileURLToPath(new URL('../../infra-migrations/', import.meta.url))`), 파일이 없으면 `openDb`가 새로 만든다(D-31) → `migrate(db, dirs, {dryRun, profile, applicationId, clock})`. `dryRun` = `--dry-run`이면서 `--db-copy-dir` **없을 때만** true(사본이 있으면 사본에 실제 적용 — T-00-04 [Brief 결정]과 일치). 실패 → `failure.exitCode`(1 또는 78) + `fatal` 로그(`reason`·`file`). 성공 → 보고(`applied`·`pending`·`schemaVersions`) 로그 후 0.
- **restore**(`mode-restore.ts`, DB-01 §12.3-3 일반부): `--from` 절대 경로 아님 → 64 · `--rewind-cursors`는 `parseJsonStrict` + `z.record(ServiceName, int ≥ 0)` 실패 → 64. `profile: 'full'` DB마다: 원본 = `<from>/<file>` 없음 → 78 · 원본을 readOnly로 열어 `APP_ID_GET` 대조·`INTEGRITY_CHECK` = `ok`(아니면 78) → 닫기 → 라이브 `<file>-wal`·`<file>-shm` 삭제(없으면 무시) → `<file>.restore-tmp`로 복사 → rename → rw 열기 → `rewindCursors` → `def.restoreCheck`(있으면, 실패 78) → `INTEGRITY_CHECK` → 닫기. `profile: 'meta'` DB(파생)는 파일·wal·shm 삭제 후 migrate. IO 오류 = 70. **라이브 파일이 닫혀 있음은 호출자(supervisor `svc.stop` 후 `svc.run_mode`)가 보장한다** [Brief 결정].
- **verify**: `def.verify` 없으면 64(`mode_unsupported`), 있으면 그 반환 코드.
- **job**: `loadSqliteRuntime()`(DB가 있으면) → `serveJob(job 목록, processJobChannel())` → 반환 코드로 exit(T-00-04 규약: 0/64/70). job 목록 = 기본 2개(`makeSnapshotJob`·`makeIntegrityJob` — `full` DB가 있을 때만) 중 `def.jobs`에 같은 `name`이 있으면 그것으로 대체 + `def.jobs`의 나머지(이름 중복 = invariant).

  1. **request id**: `/internal/` 경로이고 `x-request-id`가 ULID → 그 값, 없거나 무효 → 새 `ulid()` + (내부 경로면) `warn` `http.request_id.missing` · `/api/`는 항상 새 값(IF §2.2). 응답 `x-request-id` echo.

  3. `/api/**`·`/internal/**` 응답 `cache-control: no-store`.
  4. **종료 중** → 503 `DEP-900` + `retry-after: 1`(health 2종 제외). **준비 전**(readyz false) → 503 `DEP-901`(health·metrics 제외).
  5. **인증**: health 2종 없음 · `/internal/` = `checkInternalAccess(auth, authorization, route.allowedCallers)` → 401 `AUTH-900`/403 `ACL-900` · `/api/` = `def.publicAuth`(없는데 `/api/` 라우트를 등록하면 **등록 시 invariant**).
  6. **데드라인**: `x-fathom-deadline-ms` = `"0"` 또는 음수 정수 → 504 `DEP-902` · 정수 1~600000 → `deadlineAt = recv + v` · 그 밖 문자열 → 400 `VAL-900`(`rule: 'deadline_header'`) · 없음 → `recv + (route.deadlineMs ?? 2000)`.
  7. **쓰기 게이트**(§4.7): GET 아님 + `common.admin.*`·`common.health.*`·`common.metrics.*` 아님 → 게이트 통과 대기.
  8. **멱등 키**(`route.idempotent`): 헤더 ULID 아님·없음 → 400 `VAL-901`.
  9. **검증**: 문자열 값 전부 `normalize('NFC')`(STD-API-35, 원 객체 불변·깊이 ≤ 32) → `params`·`query`·`body`(bodyKind `ndjson`이면 body 생략) `safeParse` → 실패 400 `VAL-900` + `errors[]`(≤ 50: `path` = 이슈 경로 `.` 결합 ≤ 200, `message` ≤ 300, `rule` = 이슈 `code`). Fastify 본문 오류 매핑: `FST_ERR_CTP_BODY_TOO_LARGE` → 413 `LIMIT-900` · `FST_ERR_CTP_INVALID_MEDIA_TYPE` → 415 `VAL-904` · JSON 구문·빈 본문·`__proto__`/`constructor` → 400 `VAL-900`.

  11. **핸들러** → **응답 검증**: `route.response[status]` 없음 또는 `safeParse` 실패 → 500 `INTERNAL-901`(+ `error` 로그 — 이슈 경로만, 값 0). JSON은 파싱 결과를 `JSON.stringify`, `responseKind: 'text'`는 문자열 + `text/plain; version=0.0.4; charset=utf-8`.
  12. **멱등 저장**: 상태 < 500(핸들러가 던진 4xx `AppError`의 Problem 포함) → `complete`, 그 밖 → `abandon`(`finally`로 보장).
  13. **span 로그** 1줄(`info`, STD-LOG-10): `{event: 'span', 'http.route': route.id, 'http.status', dur_ms, outcome, trace_id, span_id}` — 본문·쿼리 값 0(STD-LOG-22). 메트릭 `http_request_duration_ms{route, status}`(버킷 `[5,10,25,50,100,250,500,1000,2500,5000]`).

### 4.7 quiesce 쓰기 게이트 (`write-gate.ts`, ADR-013 §1-2·6)

- `enter()`: 열림 → 진행 중 카운터 +1, 해제 함수 반환 · 닫힘 → 열릴 때까지 최대 `waitMs` 대기, 넘으면 `timeout`(파이프라인 7단계가 503 `DEP-900` + `retry-after: 1`).
- `quiesce`: 게이트 닫기(이미 닫혀 있으면 epoch만 교체 — ops-api가 epoch를 직렬화 **[Brief 결정]**) → `onChange('closed')`(createService가 relay·inbox·정리 타이머를 `pause`) → 진행 중 카운터 0까지 `ackDeadlineMs` 대기 → 성공 = `QuiesceAck{epoch_id, quiesced_at, in_flight_drained: true}` / 실패 = **게이트를 즉시 다시 열고** 503 `DEP-900`(`detail: 'quiesce 기한 초과'`) **[Brief 결정]**. `autoReopenMs` 안에 `resume`이 없으면 자동으로 열고 `warn` `admin.quiesce.auto_reopened`(ops-api 사망 대비) **[Brief 결정]**.
- `resume`: 열기 → `onChange('open')`(relay `resume` + `kick`) → `ResumeAck{epoch_id, resumed_at}`. 닫혀 있지 않아도 ack(멱등).

### 4.8 종료 (`shutdown.ts`, STD-ASY-12, ADR-012 §8)
1. `shuttingDown = true`(이후 새 요청 503 `DEP-900`) → 2. 진행 중 요청이 끝날 때까지 `grace_ms` 안에서 대기 → 3. relay `drainOnce()` 1회(남은 시간 안, 넘으면 포기) → `relay.stop()` · 타이머 해제 → 4. `onShutdown` 훅 **등록 역순**(각 예외는 `error` 로그 후 계속) → 5. `jobs.shutdown()` → 6. 쓰기 DB마다 `OPTIMIZE` → `close()` → 7. `fastify.close()` → 8. `port.exit(0)`. 기한 초과는 `warn` 후 다음 단계로(종료 코드는 0 유지). 두 번째 호출은 첫 호출의 Promise를 돌려준다.

### 4.9 타이머 (createService, 전부 `.unref()`, 종료 시 해제, quiesce 중 건너뜀)
- relay 안전망 500ms(§4.1.3) · `_infra` 정리: 기동 5분 후 첫 회 + 10분마다 `purgeInfraOnce`(DB-01 §15 D-16) · `WAL_CHECKPOINT_PASSIVE`: 5분마다 쓰기 DB 전부(DB-01 §3.1, 유휴 판정 없이 — PASSIVE는 대기 0) **[Brief 결정]**.
