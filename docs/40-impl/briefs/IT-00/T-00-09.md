## 4. 동작 규약

### 4.1 전사 규칙 (전 파일 공통 — T-00-02 §4.1과 동일)

1. 블록의 `export const`·주석·정규식·숫자·필드 순서를 **그대로**. 이름 변경·필드 추가·`.optional()` 추가·정규식 수정 금지. 각 `export const X = <zod>` 아래 `export type X = z.infer<typeof X>;`. 비공개 `const`(`Opt`·`Ext`·`Md`·`H`·`Base`·`Rpm`·`QuotaWin`)는 export하지 않는다.
2. 한 파일 머리가 여러 블록에 나오면 **한 파일에 문서 순서대로** 합친다.
3. 블록이 컴파일되지 않거나 서로 모순이면 고쳐 쓰지 말고 §7 `contract_change`. 단 §4.2의 [Brief 결정]은 판정이 끝났으므로 그대로 적용한다.
4. **zod 4 의미(바꾸지 말 것, 실측 4.6.5)**: `z.record(<z.enum 또는 enum들의 union>, V)`는 **전 키 필수**다. 해당 스키마: `ConceptPageContentPreSubmit.lenses`(5키) · `FpackManifest.required_for_level`(5) · `AssessmentInventory.concepts[].formats_by_mode`(4)·`assessment_pool`(5×4) · `HealthBoard.eventloop_p99_ms`(ServiceName 5) · `AiPolicyV1.cache_ttl_days.per_task`(**TaskId ∪ SystemTaskId = 35키**). 키가 정규식 문자열(`ObjKey`·`ProviderId`·`ConceptId`·`z.string()`)이면 비전수다. 원문 그대로 두고 테스트로 고정 단언한다.

### 4.7 `structuralFeasibility()` **[Brief 결정]** (SP-6 이식 → 계약 모양, FR-CUR-025·FR-PRG-013, `pack/feasibility.ts`)

```ts
export function structuralFeasibility(policy: z.infer<typeof MasteryRulesV1>, inventory: z.infer<typeof AssessmentInventory>,
  transition: FeasibilityTransition, mode: z.infer<typeof AiMode>, _sp1: z.infer<typeof Sp1State>,
): { feasible: boolean; blockers: z.infer<typeof FeasibilityBlocker>[] }
```

비공개 상수(FR-PRG-013 계약 수치 — MasteryRulesV1에 키가 없음, 주석에 FR 인용): `SPARSE_REQUIRED_LT = 3`, `D4_FLOOR = 2`, `D4_CAP = 5`, `CASE_L4_MIN = 2`, `LEVEL_KEY = { 1: '1', 2: '2', 3: '3', 4: '4' } as const`(`as` 단언 대신, STD-TS-12). `k = transition.from`.

0. `transition.track !== inventory.track` 또는 `transition.to !== k + 1` → `throw new RangeError('structuralFeasibility: invalid transition')`.
1. `all` = `inventory.concepts` 중 `level === k`. 0개면: `policy.promotion.empty_level === 'skip'` → `{feasible: true, blockers: []}` 즉시 반환, `'block'` → `EMPTY_LEVEL` 하나만 담아 즉시 반환.
2. `pool = inventory.assessment_pool[LEVEL_KEY[k]][mode]`. `pool.items < policy.assessment.items` 또는 `new Set(pool.formats).size < policy.assessment.formats_min` → `NO_ASSESSMENT_POOL`.
3. `required` = `all` 중 `required_for_level !== null`, `concept_id` 오름차순. `required.length >= SPARSE_REQUIRED_LT`면 각 개념의 `new Set(formats_by_mode[mode]).size < policy.mastery.formats_min` → `MASTERY_FORMATS<3:<concept_id>`. 미만(희소 레벨)이면 blocker 없음(깊이 자산은 런타임 판정 몫 — 계약 code 집합에 없음).
4. `k === 2`: `possible` = `inventory.concepts` 중 `d4_possible` 이고 (`policy.d4.possible_scope === 'level_le_k'`면 `level <= k`) 인 수. `need` = `floor_mode === 'min_with_possible'` → `Math.max(Math.min(D4_FLOOR, possible), Math.min(D4_CAP, possible))`, `'fixed'` → `Math.max(D4_FLOOR, Math.min(D4_CAP, possible))`. `possible < need` → `D4_POSSIBLE<REQUIRED`.
5. `k === 4`: `inventory.cases` 중 `level >= 4` 수 `< CASE_L4_MIN` → `CASE_L4+<2`. (`k === 3` Case 검사는 계약 code가 없어 생략.)
6. 순서 = 위 단계 순, `detail_ko` 고정 문구: `L${k} 개념 0개` · `L${k} ${mode} 승급 평가 풀 부족: 문항 ${items}/${need}, 형식 ${f}/${fmin}` · `${concept_id} 숙달 산입 형식 ${n}/${min}` · `D4 가능 개념 ${possible} < 필요 ${need}` · `L4+ Case ${n}/2`. `feasible = blockers.length === 0`. 같은 입력 = 같은 출력(전역 상태·시계 0).
